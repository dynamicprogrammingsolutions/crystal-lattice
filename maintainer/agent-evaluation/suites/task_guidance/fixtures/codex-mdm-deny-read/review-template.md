## Review checklist

- [ ] Requirements describe verifiable outcomes rather than execution steps.
- [ ] Supporting details explain the requirements without becoming hidden requirements or execution steps.
- [ ] Requirement questions and decisions changing scope or outcomes are easy to find near the top.
- [ ] The requested retain-plan or omit-plan handoff is followed in substance, not only by heading names.
- [ ] Human-facing sections are concise while supporting details preserve enough durable context for continuation.
- [ ] The user-facing response is self-contained and easier to review than the full stored plan.

For retain-plan and existing-task-plan only:

- [ ] A substantive free-form plan body after status preserves the approach and execution details another agent needs.
- [ ] Important implementation decisions and open implementation questions are collected immediately before documentation, followed by checkbox tasks and verification.
- [ ] Requirement verification maps each requirement or group to observable acceptance evidence at a user-relevant or public boundary.
- [ ] Implementation-specific robustness checks are separate from requirement acceptance evidence.
- [ ] Documentation is presented separately with its audience and intended use, or the response states that no documentation change is planned.

For omit-plan only:

- [ ] Planned implementation details, decisions or questions, risks, documentation, tasks, and verification are absent in substance rather than relabeled.
- [ ] Existing-test or documentation facts in supporting context are not mistaken for a required plan.
