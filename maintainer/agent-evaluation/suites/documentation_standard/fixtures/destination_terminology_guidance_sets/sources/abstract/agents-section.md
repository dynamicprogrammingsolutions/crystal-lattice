Treat prompts, conversations, tasks, specifications, existing files, and
review comments as input material that explains required behavior. Choose
terminology and organization for the maintained destination; do not copy
labels or structure between artifacts. When a destination already contains
planning or tracking terminology, replace it unless required or established by
the product, public interface, or destination domain.

Examples: a task heading named “Deployment workstream” does not become a
specification heading; an inherited “Implementation checkpoint” heading in
user documentation is replaced with the supported capability; an established
public `retry_after` field remains exact.
