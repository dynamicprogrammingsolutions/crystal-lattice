Use requests, conversations, tasks, specifications, existing files, and review
comments to understand required behavior. In the file or record you create or
change, choose terminology and organization for its purpose, readers, and
interfaces. Do not copy labels or structure from another context. Replace
inherited planning or tracking terminology unless it is required or
established by the product, public interface, or relevant domain.

Examples: a task heading named “Deployment workstream” does not become a
specification heading; an inherited “Implementation checkpoint” heading in
user documentation is replaced with the supported capability; an established
public `retry_after` field remains exact.
