- Existing service tests use FastAPI `TestClient` and only assert that the

## Execution plan

Status: Draft

### Design and boundaries

First write the approved contract in the cross-boundary specification. Add
validated route inputs with defaults that preserve the no-query branch, then
pass normalized values to a CRUD query function. Keep the query endpoint at
`/notes/`; do not add a second route that would let the client and CLI drift
from the existing collection resource.

The CRUD query should compose the optional text predicate, an allow-listed
primary sort expression, an explicit ID tie-breaker, and bounded offset/limit
clauses in that order. The exact expressions and response shape follow the
approved contract. Do not add schema changes unless the resolved contract
requires a field that does not exist; the current title and description
columns are sufficient for the proposed filter.

### Dependencies and sequencing

This subtask is the contract gate. Review its specification and route tests
before starting the client or CLI subtasks. It has no repository subtask
dependency, but it cannot be marked complete until the public choices are
approved.

### Risks and mitigations

- An unallow-listed sort field could become a SQL injection or compatibility
  problem; map public values to fixed SQLAlchemy columns.
- A primary sort without an ID tie-breaker makes page boundaries unstable;
  test repeated equal-key records explicitly.
- Applying a default limit to the no-query branch would break the current
  collection behavior; retain a separate compatibility path as specified.
- Database-specific string matching can vary; test the documented case and
  substring behavior through the HTTP route.

### Implementation decisions and open questions

No API-specific public decision is final until the parent questions are
resolved. The implementation may choose internal helper names and query
composition, but it must not invent defaults or error responses.
