# Blog archive pagination

Split the `/blog/` archive into stable pages of at most 20 posts each with
accessible previous/next navigation, preserving every other generated surface
(home, tags, feed, sitemap, individual posts), post order, and the static
zero-JavaScript output.

## Requirements checklist

- [ ] `/blog/` remains the first archive page and shows the newest posts.
- [ ] Each archive page contains at most 20 posts; later pages are generated by
      the production build only when posts exceed 20.
- [ ] Later archive page URLs are stable and deterministic (format per D1 below,
      e.g. `/blog/2/`, `/blog/3/`, …); `/blog/` is not duplicated at `/blog/1/`.
- [ ] Every archive page with a newer or older sibling exposes accessible
      previous/next navigation: real links with discernible accessible names,
      `rel="prev"`/`rel="next"`, inside a labelled `nav` landmark. Links are
      omitted (not rendered disabled) when no sibling page exists.
- [ ] Post order is preserved: newest-first within each page, and pages continue
      in one strict newest-to-oldest sequence across pages with no gaps or
      duplicates (page 1 holds the newest posts).
- [ ] Home page is unchanged: URL and latest-3-posts list behavior.
- [ ] Tag pages are unchanged: per-tag listings and `/tags/<tag>/` URLs.
- [ ] Feed is unchanged: `/feed/feed.xml` still lists all posts.
- [ ] Sitemap continues to enumerate the site's public pages; existing entries
      are unchanged. New archive pages may appear as additional entries (see F8).
- [ ] Individual posts are unchanged: post URLs, post layout, and the links to
      individual posts from lists (individual-post navigation preserved).
- [ ] Output remains static HTML with zero client-side JavaScript.
- [ ] Maintained documentation reflects the paginated archive in the same change
      (README archive claim; `docs/development` archive-pagination spec and
      `docs/development/index.md` line), per AGENTS.md documentation policy.

## Decisions and open questions

- D1 (material, needs confirmation): URL format for later archive pages.
  Recommendation: `/blog/<pageNumber>/` with page 1 implicit at `/blog/`
  (e.g. `/blog/2/`, `/blog/3/`). Short, stable, no duplicate first-page URL.
  Alternative: `/blog/page/2/`. Affects the public URL contract, so it is
  resolved at plan approval.
- D2 (minor, presented for approval with the plan): navigation wording —
  "Newer posts" for the previous (lower-numbered) page, "Older posts" for the
  next (higher-numbered) page, plus a "Page N of M" indicator in the nav.
- A1 (assumption): "stable later pages" means deterministic position-based URLs
  (`/blog/2/` always exists once enough posts exist). With newest-first
  ordering, adding posts shifts which posts sit on which page; that is inherent
  to a paginated date-ordered archive. If content-stable URLs (e.g. date-based
  archive pages) were intended, that is a materially larger design and must be
  confirmed before execution.

## Supporting facts

All facts below are from direct inspection of this repository.

- F1: `content/blog.njk` is a single page (`permalink: /blog/`) that sets
  `postslist = collections.posts` and includes `_includes/postslist.njk`.
- F2: `_includes/postslist.njk` renders `postslist | reverse`, so it shows any
  list newest-first. It is shared by the home page (`collections.posts |
  head(-3)`) and tag pages (`collections[tag]`). Consequently a paginated
  archive whose pagination data is already newest-first must NOT reuse this
  include unchanged — it would double-reverse and show oldest-first.
- F3: Eleventy collections (`collections.posts`) sort oldest→newest; current
  display order comes from the `| reverse` in F2. Pagination chunks the data
  array in order, so pagination needs `reverse: true` (reverses the whole data
  set before chunking) for page 1 to hold the newest posts.
- F4: Eleventy pagination exposes `pagination.pageNumber` (0-based),
  `pagination.pages.length`, `pagination.href.previous`, `pagination.href.next`,
  and `alias` for the per-page chunk. `permalink` supports Nunjucks, enabling a
  first page without a number and later pages with one.
- F5: `content/tag-pages.njk` paginates `collections` independently (filter
  `[all, posts]`) and is unaffected by changes to `blog.njk`.
- F6: `content/feed.xml.njk` iterates `collections.posts` (posts only, all of
  them); `content/sitemap.xml.njk` iterates `collections.all`, so newly
  generated archive pages will appear in the sitemap automatically (F8) and the
  feed needs no change.
- F7: `tests/archive-output.test.js` contains only a comment — there is no real
  test coverage today; `npm test` passes vacuously. The fixture has 2 posts
  (`content/posts/`), so a single-page archive is expected until content grows;
  multi-page behavior must be evidenced by building the real site with >20
  generated posts in a temp workspace (real config, real includes, real build —
  no mocked output).
- F8: Sitemap/`collections.all` consequence: `/blog/2/`+ pages become public
  pages and gain sitemap entries. Existing entries are unchanged. Accepted
  consequence of pagination; documented in the spec.
- F9: `README.md` claims the build produces "a home page, blog archive, tag
  pages, feed, sitemap, and individual posts without client-side JavaScript";
  `docs/development/index.md` states "No archive pagination specification
  exists." Both must be updated in the same change as the feature.
- F10: Upstream Eleventy Base Blog at the pinned commit (per `UPSTREAM.md`)
  also renders a single-page archive; the URL format is a fresh decision, not
  an upstream convention.
- F11: `node_modules/` is not installed in this worktree; the executor will
  need `npm install` before building/testing (`@11ty/eleventy ^3.0.0`).

## Execution plan

Status: Draft

### Design

`content/blog.njk` becomes an Eleventy-paginated template and stays the single
source of the archive:

- Frontmatter pagination over `collections.posts` with `size: 20`,
  `reverse: true`, and `alias: postslist` (F3). The chunk is newest-first.
- `permalink` expression: `/blog/` for page 0, `/blog/<pageNumber | plus: 1>/`
  for later pages (D1). Eleventy generates later pages only when the data set
  exceeds one chunk, so the 2-post fixture keeps producing a single page.
- The body renders the chunk directly (`for post in postslist`) instead of
  including `postslist.njk`, avoiding the double-reverse in F2. The include and
  its consumers (home, tags) are untouched. The few duplicated list-markup
  lines are accepted to avoid changing shared include semantics.
- Main heading is `Archive` on page 1 and `Archive, page N` on later pages so
  each page is distinguishable.
- Below the list, a pagination `nav` landmark (`aria-label="Blog pages"`)
  renders at most two real links: `rel="prev"` → "Newer posts" to
  `pagination.href.previous` when present, `rel="next"` → "Older posts" to
  `pagination.href.next` when present, plus a "Page N of M" text indicator
  (D2). No dead or disabled links are emitted; no JavaScript.

Nothing else in the site changes: home, tags, feed, individual post layout, and
post URLs stay as-is; the sitemap picks up new archive pages automatically
(F5–F8).

Verification crosses the real production build: tests run Eleventy against a
temp workspace that mirrors the repo layout (real `eleventy.config.js`, real
`_includes`, generated synthetic posts) plus a build of the committed content,
then assert over the emitted files and HTML. Tests never hand-assemble expected
HTML or mutate repo content (F7).
