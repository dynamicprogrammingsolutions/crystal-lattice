# Homepage First-User Release Image Plan

Status: **Draft shortlist for owner review — no source promotion.**

Updated: 2026-10-23

## Objective

Select and produce the smallest visual set that explains the application,
supports the approved copy, and leaves no retained placeholder. Each image
owns one primary visitor-facing claim.

The current Candidate A images remain ignored comparison material. Approval of
this plan does not approve those exact derivatives.

## Shared capture identity

Use one sanitized deterministic fixture family:

- workspace: `Starlette compatibility`;
- session slugs and visible IDs use descriptive public-safe text;
- standard Crystal Lattice blue accent where the product surface permits it;
- no user home paths, personal repository names, credentials, private URLs,
  raw UUIDs, or active live sessions;
- matching light and dark sources where the maintained pipeline supports both;
- genuine production components and native capture paths.

## Capture requirements

### HOME-OVERVIEW-01

The native source should show:

- three sessions with descriptive titles and subtitles;
- selected session;
- pinning and durable status where readable;
- one truthful current request state;
- selected conversation;
- composer;
- selected profile/model identity.

Do not create a second enlarged session-row panel in the public figure. If
session-row text is unreadable, reduce the actual capture window's irrelevant
conversation content or adjust the source window before capture.

### HOME-PROFILE-01

The current full picker has too much unused list/window space at inline size.
Create a dedicated website capture state:

- native window approximately 880–980 by 620–720 points, adjusted after direct
  review;
- two or three profiles total;
- selected profile detail visible without scrolling;
- contributed tools visible;
- no source text modification during processing.

### HOME-CONTINUITY-01

Capture Desktop and mobile independently so each can receive its own frame and
responsive sizing.

Shared fixture values:

- title: `Starlette compatibility`;
- profile: one selected public-safe profile;
- task status: matching where visible;
- prompt: one short request;
- response: one short matching response;
- no raw session UUID.

The website composition must not blend the clients into one apparent product
window.

## Derivative and figure treatment

For each approved source:

- retain a reviewed source master under `visual_assets/sources/`;
- generate optimized light/dark derivatives through the catalog;
- preserve exact source dimensions, crop, and fixture revision in the asset
  record;
- generate a focused thumbnail separately from an optional full-size source
  when the inline image cannot carry secondary details;
- keep title and caption in structured page content rather than painting text
  into the image;
- use CSS frames where approved instead of baking decorative frames into the
  source raster.

## Readability review

Create one contact sheet per theme and one actual-page review:

1. source candidates at native size;
2. proposed inline derivatives at their target CSS widths;
3. 1440-, 768-, 390-, and 320-pixel page captures;
4. side-by-side comparison of apparent UI label size.

Reject or recapture an image when:

- the primary control or label is not readable inline;
- a large unused region dominates the source;
- a caption is required to explain what should be visually obvious;
- a device frame reduces proof-bearing UI below the target size;
- a source appears missing, transparent, or visually blank;
- two images make the same claim.

## Placeholder disposition

No placeholder is filled merely to preserve the old component structure.

Retain with real proof:

- complete application overview;
- visible response information;
- compact profile setup;
- provider controls;
- Desktop/mobile continuity;
- Desktop connection;
- mobile connection.

Remove or route elsewhere:

- separate Composer tour;
- Composer actions;
- Message actions;
- Session actions;
- compiled-instructions tour;
- duplicate usage/report visual;
- bridge deployment walkthrough;
- unverified SDK example;
- duplicated model-family gallery;
- disabled waitlist prototype.

## Approval questions

1. Does the large Desktop overview replace the separate Composer and Workspace
   stories?
2. Are visible, configurable, and extensible the correct three focused proof
   relationships?
3. Is provider usage/cost the correct visibility proof?
4. Is provider controls sufficient extensibility proof, or is a focused
   Plugins dialog required instead?
5. Should inline figures offer enlargement, or must every primary detail be
   readable without it and full sources remain documentation-only?
6. Are restrained macOS and phone frames appropriate for overview and
   continuity while focused callouts remain unframed?
