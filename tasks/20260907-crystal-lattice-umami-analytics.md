# Add privacy-safe Umami analytics to the Crystal Lattice public sites

## Description

Add basic self-hosted Umami analytics to `https://crystallattice.dev` and
`https://docs.crystallattice.dev`. Keep their metrics separate, disclose the
processing accurately, provide a browser-level opt-out, and preserve
analytics-free local and unconfigured builds.

Reuse the Dynamic Programming Solutions Umami installation at
`https://stats.dynamicprogrammingsolutions.com`. Do not enable advertising,
remarketing, session replay, heatmaps, identification, session properties, or
arbitrary custom events.

## Requirements checklist

- [x] Umami contains separate website records for `crystallattice.dev` and
      `docs.crystallattice.dev`, with distinct public identifiers and
      replay/heatmaps disabled.
- [x] Every production page on each domain loads exactly one privacy-restricted
      tracker for its own website record.
- [x] Missing or invalid analytics configuration builds successfully with no
      tracker markup or collection requests.
- [x] Tracking runs only on each exact approved hostname, respects Do Not Track
      and browser opt-out, and excludes URL queries, fragments, advertising
      click identifiers, and referrer queries, credentials, and fragments.
- [x] The baseline accepts only page views and Core Web Vitals and rejects
      identification, session properties, custom events, replay, and heatmaps.
- [x] The Privacy Policy distinguishes application data from public-site
      analytics and discloses the controller, purposes, categories, legal
      basis, infrastructure/location, retention, browser preferences, opt-out,
      and data-subject rights.
- [x] Visitors can disable or re-enable analytics from the Privacy Policy with
      an accessible browser-local control.
- [x] The documentation site exposes a discoverable link to the shared Privacy
      Policy on `crystallattice.dev`.
- [x] Both sites remain functional when analytics is absent, blocked, slow, or
      unavailable.
- [x] Production uses environment configuration rather than committed UUIDs,
      and live verification confirms record isolation and sanitized storage.

## Unresolved requirement questions and decisions

None.

Approved decisions:

- Use two Umami website records so overlapping landing and docs paths remain
  distinguishable.
- Use the existing self-hosted `/insight.js` and `/collect` endpoints.
- Use the restricted consentless audience-measurement baseline with a clear
  opt-out and Do Not Track support; do not show a consent popup.
- Enable Core Web Vitals under the same sanitizer and disclosure.
- Keep replay, heatmaps, advertising, remarketing, identification, session
  properties, and custom events disabled.
- Publish one Privacy Policy on the landing site covering both domains and link
  to it from the documentation site.

## Supporting details

- `landing_page/` is an Astro 5 static site; its shared shell is
  `landing_page/src/layouts/Layout.astro`.
- `docs_site/` is generated by MkDocs Material. `docs_site/prepared/` and
  `docs_site/dist/` are generated and must not be edited directly.
- `.github/workflows/deploy-static-sites.yml` builds and deploys both sites.
- Hosting uses private S3 origins and CloudFront. The current response-header
  policy does not set Content Security Policy.
- The landing footer already links to `/privacy`; docs has no Privacy link.
- The current policy says the website does not use analytics. Its statement
  that Crystal Lattice applications contain no analytics remains accurate.
- Public tracker: `https://stats.dynamicprogrammingsolutions.com/insight.js`.
- Public collector: `https://stats.dynamicprogrammingsolutions.com/collect`.
- UUIDs are public configuration, not credentials, but must come from actual
  Umami records.
- Existing Umami retention is up to two years and its database is hosted on AWS
  infrastructure in Ireland.
- A Crystal Lattice sanitizer is required because the DPS website sanitizer is
  not a global Umami policy.
