# Provider-Extension Session Settings Lifecycle

Short description: Add a generic capability that lets non-application plugins initialize and mutate per-session settings/overrides through lifecycle-triggered paths, so provider extensions and similar plugin types can support session-owned settings without being forced into application plugins.

## Motivation

Several features want session-owned settings that are not purely application-plugin concerns.

Examples:

1. `openai_responses` prompt caching needs a session-owned `prompt_cache_key` that can be:
- auto-created for new sessions
- preserved on fork
- visible/editable in normal session settings UI
- regenerated by a provider-extension session action
2. Similar future features may need to initialize or repair per-session settings on lifecycle events such as:
- session creation
- first request / pre-send fallback for legacy sessions
- future session migration or repair flows

Today, application plugins can mutate sessions directly, and provider extensions can execute explicit session actions, but non-application plugins do not have a generic lifecycle path for session-settings writes.

## Problem statement

We need a reusable capability for non-application plugins to participate in session settings lifecycle without collapsing provider-owned behavior into application plugins or pushing provider-specific logic into the application layer.

The capability must be generic:

1. not OpenAI-specific
2. not limited to prompt caching
3. compatible with existing per-session overrides/session settings flows
4. compatible with fork semantics where session-owned settings should normally be preserved unless a feature explicitly chooses otherwise

## Architectural intent

1. Provider stays transport/native-history focused.
2. Capability-specific request shaping remains in provider extensions/features.
3. Session settings remain part of session-owned state and should flow through existing session settings UI/endpoints where possible.
4. Shared application/core/server changes should expose generic hooks/helpers rather than embedding feature-specific logic.

## Expected outcome

After this task, a provider extension or similar non-application plugin type should be able to:

1. initialize session-owned settings during session creation
2. apply fallback/repair writes during lifecycle-triggered request flows when needed
3. rely on normal session settings surfaces to display/edit those values
4. combine lifecycle writes with explicit session actions when a user-triggered mutation is needed
