# Cloud Agent Config Reference Audit And Typing
Audit the `plugins/cloud-agent-app` config reference against the implemented `application.cloud_agent` surface, then update the docs so every documented key has a type and the reference is structured around dotted config paths and object shapes rather than only broad sections.

## Requirements checklist

- [ ] Audit the current cloud-agent config reference and compare it against the actual editable config surface implemented in code.
- [ ] Restructure the config reference so top-level object keys are documented explicitly, including nested object shapes such as `transfer_up_profiles`, `sync_down_profiles`, `container_profiles`, `managed_ssh`, `config_assets`, and `runtime_env`.
- [ ] Document each editable config key with at least its type and description; include required/default information where the code defines clear behavior.
- [ ] Use dotted config paths for nested keys, for example `transfer_up_profiles.<profile_id>`, `transfer_up_profiles.<profile_id>.label`, and similar entries for all nested keys.
- [ ] Distinguish user-editable config keys from derived/internal runtime state and deprecated aliases.
- [ ] Add documentation for the startup/poll timeout knobs and other currently implemented but undocumented cloud-agent settings.
- [ ] If adding automated verification, do not use a hard-coded expected key set; only add a test if the key inventory can be collected deterministically from a structured source of truth.

## Background

The current config reference in `plugins/cloud-agent-app/README.md` documents
the main sections, but it is incomplete and under-typed. In particular, it
does not currently give a full per-key type-oriented reference for the
implemented `application.cloud_agent` config surface.

The desired documentation structure is:

- top-level key entries for object-valued settings such as
  `application.cloud_agent.transfer_up_profiles`
- object-shape entries for profile maps, for example
  `application.cloud_agent.transfer_up_profiles.<profile_id>`
- dotted-path entries for nested fields, for example
  `application.cloud_agent.transfer_up_profiles.<profile_id>.label`
- explicit type information for every documented key

The user also requested that verification must not rely on a hand-maintained
hard-coded key set. A unit test is acceptable only if the implemented config
key inventory can be collected deterministically from a structured source of
truth.

## Current Audit Findings

The current README reference starts at:

- `plugins/cloud-agent-app/README.md` under `## Config Reference`

It is missing or underspecifying several implemented user-facing keys.

Known implemented keys that are currently undocumented in the config
reference:

- `application.cloud_agent.startup_poll_timeout_seconds`
- `application.cloud_agent.startup_wait_timeout_seconds`
- `application.cloud_agent.start_action_timeout_seconds`
- `application.cloud_agent.startup_start_timeout_seconds`
- `application.cloud_agent.startup_poll_interval_seconds`
- `application.cloud_agent.transfer_public_host`
- `application.cloud_agent.optimize_runtime_config`
- `application.cloud_agent.imported_branch_prefix`

The current docs also do not clearly document some important type/shape
behavior:

- script fields support `string` or ordered fallback `string[]`
- profile sections are object maps keyed by non-empty profile ids
- `managed_ssh.extra_rsync_args` is `string[]`
- `disabled_plugins` is `string[]`
- `config_assets.exclude` is `string[]`
- `runtime_env.include`, `runtime_env.exclude`, and `runtime_env.env_files`
  are `string[]`

The docs should not present these as editable config keys:

- `selected_transfer_up_profile`
- `selected_sync_down_profile`
- `selected_container_profile`
- `runtime_image`
- resolved script-path state such as `local_stage_script`,
  `cloud_setup_script`, `cloud_export_script`, and similar derived values

Those are derived runtime state emitted by the resolver rather than user input.

## Recommended Documentation Shape

Prefer a reference structure like:

1. `application.cloud_agent`
2. `application.cloud_agent.transfer_up_profiles`
3. `application.cloud_agent.transfer_up_profiles.<profile_id>`
4. `application.cloud_agent.transfer_up_profiles.<profile_id>.label`
5. `application.cloud_agent.transfer_up_profiles.<profile_id>.local_stage_script`
6. `application.cloud_agent.transfer_up_profiles.<profile_id>.local_transfer_script`
7. `application.cloud_agent.transfer_up_profiles.<profile_id>.cloud_setup_script`
8. `application.cloud_agent.transfer_up_profiles.<profile_id>.install_script`
9. `application.cloud_agent.transfer_up_profiles.<profile_id>.validation_script`
10. `application.cloud_agent.transfer_up_profiles.<profile_id>.compatible_sync_down_profiles`

Repeat the same pattern for:

- `sync_down_profiles`
- `container_profiles`
- `managed_ssh`
- `config_assets`
- `runtime_env`

For each key, the target format should include at least:

- `Type`
- `Description`

When the code defines stable behavior, also include:

- `Required`
- `Default`
- `Notes`
