# Cloud Orchestrator Deploy E2E Source Bundle Coverage
Improve cloud orchestrator E2E coverage so tests better match real deployment
paths and catch missing files in reduced deploy build contexts before a remote
deploy fails.

## Requirements checklist

- [ ] Make the default local Docker cloud orchestrator E2E build runtime images
  from the same source bundle used by deploy scripts, not directly from the
  repository root.
- [ ] Harden AWS EC2 cloud orchestrator E2E so it can force fresh image builds
  from the current source bundle and avoid silently validating stale images.
- [ ] Add or document a gated remote-docker deploy E2E that directly invokes
  `cloud-orchestrator/deploy/remote-docker/deploy.sh` against an explicit SSH
  target and then runs the existing external cloud-instance E2E flow.
- [ ] Keep deploy logic centralized. Tests may call deploy/source-bundle
  helpers and scripts, but should not duplicate the logic in deploy scripts.

## Background

The remote Docker deployment failed because
`cloud-orchestrator/runtime/python/Dockerfile` now expects:

```text
scripts/build_cloud_runtime_plugin_bundle.py
```

but the shared deployment source bundle originally included only:

```text
cloud-orchestrator
core/python
application/python
plugins
```

Local repository-root Docker builds did not catch this because the missing
script exists in the normal checkout. The immediate fix was to include the
script in `cloud-orchestrator/deploy/lib/source_bundle.sh` and add a focused
source-bundle content regression test.

The broader test gap remains: existing local Docker E2E verifies the runtime
image and orchestration flow, but it builds from the checkout root rather than
from the reduced deployment source bundle. That means it can still miss errors
where a Dockerfile works from the checkout but fails from the deploy bundle.

## Existing Test Coverage

### Local Docker E2E

Current command:

```bash
RUN_CLOUD_ORCHESTRATOR_E2E=1 npm test --prefix packages/frontend-sdk -- cloud-orchestrator.e2e
```

Current behavior:

- builds `cloud-agent-runtime:latest` from the repository root;
- builds `cloud-agent-transfer-ssh:latest`;
- starts the orchestrator locally through `mix run --no-halt`;
- calls the application action `cloud.start_session_agent`;
- waits for the cloud instance to reach `running`;
- connects with `CloudTransport`;
- verifies cloud sessions/messages/workspace transfer/sync-down.

Gap:

- it does not use the reduced deploy source bundle, so it cannot catch files
  omitted from `create_cloud_orchestrator_source_bundle`.

### AWS EC2 E2E

Current command shape:

```bash
RUN_CLOUD_ORCHESTRATOR_E2E=1 \
RUN_AWS_CLOUD_ORCHESTRATOR_TESTS=1 \
CLOUD_ORCHESTRATOR_E2E_MODE=aws-ec2-cloudfront \
npm test --prefix packages/frontend-sdk -- cloud-orchestrator.e2e
```

Current behavior:

- calls `cloud-orchestrator/deploy/aws-ec2/up.sh`;
- provisions/starts the deployed orchestrator stack;
- waits for orchestrator health;
- runs the same app action and cloud-instance flow;
- tears down through `down.sh`.

Gap:

- `up.sh` expects prebuilt image URIs. If `deploy/aws-ec2/build.sh` was not run
  from the current source bundle with the same `AWS_STACK_NAME`/tag, the E2E can
  validate stale images.

### Remote Docker Deploy

Current deploy path:

```text
cloud-orchestrator/deploy/remote-docker/deploy.sh
```

Gap:

- no E2E currently creates the source bundle, rsyncs it to a remote Docker host,
  builds there, starts compose, verifies health, then starts and validates a
  cloud instance.

## Recommended Implementation Plan

1. Update local Docker E2E image building to use the deploy source bundle.
   - In `packages/frontend-sdk/src/integration/harness.ts`,
     `startCloudOrchestratorLocal()` should call the existing
     `create_cloud_orchestrator_source_bundle` helper through bash.
   - Extract the tarball into a temp build root.
   - Run the existing Docker build commands from that extracted root:

     ```bash
     docker build -t cloud-agent-runtime:latest -f cloud-orchestrator/runtime/python/Dockerfile .
     docker build -t cloud-agent-transfer-ssh:latest cloud-orchestrator/transfer/managed-ssh
     ```

   - Continue starting the orchestrator locally with `mix run --no-halt`.
   - Clean up the extracted temp build root during E2E teardown.

2. Add local E2E assertions that reveal bundle/build-context mistakes.
   - The current source-bundle regression test should remain as a fast focused
     check.
   - The local Docker E2E should fail naturally if the runtime Dockerfile
     references files missing from the deploy source bundle.
   - Avoid duplicating file lists in the TypeScript harness beyond calling the
     shared bundle helper.

3. Harden AWS EC2 E2E against stale images.
   - Add an opt-in env var such as
     `CLOUD_ORCHESTRATOR_E2E_BUILD_IMAGES=1`.
   - When set, `startCloudOrchestratorAwsEc2()` should run
     `cloud-orchestrator/deploy/aws-ec2/build.sh` before `up.sh`.
   - Prefer a unique `IMAGE_TAG` for E2E runs, for example timestamp plus git
     SHA, unless the caller explicitly sets one.
   - Ensure the `up.sh` call uses the image URIs/state produced by that build.
   - Document that the non-build mode can validate prebuilt images and may be
     stale if reused intentionally.

4. Add a separate gated remote-docker deploy E2E.
   - Do not make this part of the normal local E2E because it needs SSH, rsync,
     a remote Docker host, host data cleanup policy, and public networking.
   - Suggested env gate:

     ```bash
     RUN_CLOUD_ORCHESTRATOR_REMOTE_DOCKER_E2E=1
     CLOUD_ORCHESTRATOR_REMOTE=...
     CLOUD_ORCHESTRATOR_PUBLIC_URL=...
     CLOUD_ORCHESTRATOR_REMOTE_DIR=...
     CLOUD_ORCHESTRATOR_HOST_DATA_DIR=...
     SSH_OPTS=...
     ```

   - The test/script should invoke
     `cloud-orchestrator/deploy/remote-docker/deploy.sh` directly.
   - After deploy succeeds, run the existing external-mode cloud orchestrator
     E2E against `CLOUD_ORCHESTRATOR_PUBLIC_URL`.
   - Decide explicitly whether the test tears the deployment down or leaves it
     running. If it leaves it running, document that behavior clearly.

5. Documentation.
   - Update `cloud-orchestrator/README.md` and
     `packages/frontend-sdk/src/integration/__tests__/README.md` with:
     - local Docker E2E now uses the deploy source bundle for image builds;
     - AWS E2E fresh-build mode and stale-image caveat;
     - remote-docker gated E2E usage.

6. Verification.
   - Fast focused checks:

     ```bash
     PYTHONPATH=core/python:application/python pytest application/python/tests/test_cloud_orchestrator_source_bundle.py -q
     PYTHONPATH=core/python:application/python pytest application/python/tests/test_cloud_runtime_plugin_bundle_builder.py -q
     ```

   - Local Docker E2E:

     ```bash
     RUN_CLOUD_ORCHESTRATOR_E2E=1 npm test --prefix packages/frontend-sdk -- cloud-orchestrator.e2e
     ```

   - AWS fresh-build E2E, when credentials and cost approval are available:

     ```bash
     RUN_CLOUD_ORCHESTRATOR_E2E=1 \
     RUN_AWS_CLOUD_ORCHESTRATOR_TESTS=1 \
     CLOUD_ORCHESTRATOR_E2E_MODE=aws-ec2-cloudfront \
     CLOUD_ORCHESTRATOR_E2E_BUILD_IMAGES=1 \
     npm test --prefix packages/frontend-sdk -- cloud-orchestrator.e2e
     ```

   - Remote Docker E2E, only when a target host is explicitly provided.
