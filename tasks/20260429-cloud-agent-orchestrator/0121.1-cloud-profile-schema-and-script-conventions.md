# Cloud Profile Schema And Script Conventions
Refine the cloud profile schema and bundled script layout so profile script locations are derivable by convention, standard repo-local hooks are optional, validation has a stable hook contract, and every bundled script is self-documented.

This task defines the validation hook contract as part of the cloud profile
schema and documentation, but it does not implement the validation command or
the end-to-end execution/testing flow for that hook.

## Requirements checklist

- [ ] Remove redundant `cloud_setup_profile` and `install_profile` references from `transfer_up_profiles`, replacing them with direct `cloud_setup_script` and `install_script` fields.
- [ ] Make `local_stage_script` and `install_script` repo-local optional hooks under the current working directory, and skip them cleanly when the file does not exist.
- [ ] Define one standard optional repo-local validation hook convention, with a stable config/schema field and default path under `${env:WORKING_DIR}` for project-specific cloud validation after transfer, setup, and install.
- [ ] Keep the shipped standard transfer/setup/sync-down scripts as the default flow, so projects can usually customize cloud behavior with repo-local hooks instead of project-specific profile overrides.
- [ ] Reorganize bundled scripts under `application/python/agent_terminal_app/default_config/cloud-agent/profiles/` so their paths are derivable directly from config keys and profile ids.
- [ ] Define and apply one stable naming convention for bundled transfer-up and sync-down script paths.
- [ ] Add clear header comments to every bundled script covering purpose, required env vars, expected inputs/outputs, and customization guidance.
- [ ] Update resolver, plugin, runtime, docs, and tests to match the simplified schema and optional-hook behavior.
- [ ] Make `plugins/cloud-agent-app` the primary documentation home for the cloud profile/reference docs, with a thorough reference that explains each config option and includes at least one complete example config using the new conventions.
- [ ] Keep `application/python/README.md` and related application docs at the high-level or quick-start layer, linking to the plugin-owned reference rather than duplicating every config detail.
- [ ] Preserve the current shipped profile behaviors and the local-Docker orchestrator profile e2e coverage while making these structural changes.

## Background

Task `0121` introduced:

- bundled default cloud profile families
- a separate `cloud_setup_profiles` section
- optional `local_stage_script` support
- local-Docker orchestrator e2e coverage for the shipped standard profile families

After review, the next refinement should simplify the configuration and make the shipped script layout easier for users to navigate and customize without consulting the code or config implementation details.

This task is intentionally the contract-definition half of the work:

- define what the validation hook is called
- define where it lives by default
- define how config resolves it
- document how users should think about it

The follow-up task implements the command that actually executes that hook and
owns the end-to-end validation test matrix.

The requested adjustments are:

- flatten `transfer_up_profiles` so each entry directly names its `cloud_setup_script` and `install_script`
- make `local_stage_script` and `install_script` point into `${env:WORKING_DIR}` and no-op when absent
- define a standard project validation hook so repos can opt into cloud validation without inventing custom profiles
- keep standard shipped profiles as the normal path, with repo-local hooks handling project-specific additions such as staging `.env` or bootstrapping a venv
- make bundled script locations follow a stable convention that matches the config structure
- document every bundled script in-place

## Proposed Direction

The follow-up should simplify the shape of `transfer_up_profiles` to something conceptually like:

```jsonc
"transfer_up_profiles": {
  "working-tree-current-state": {
    "local_stage_script": "${env:WORKING_DIR}/.cloud-agent/local-stage",
    "local_transfer_script": "${env:CONFIG_DIR}/cloud-agent/profiles/transfer_up/working-tree-current-state/local_transfer_script",
    "cloud_setup_script": "${env:CONFIG_DIR}/cloud-agent/profiles/transfer_up/working-tree-current-state/cloud_setup_script",
    "install_script": "${env:WORKING_DIR}/.cloud-agent/install-cloud",
    "compatible_sync_down_profiles": ["working-tree-patch"]
  }
}
```

And the same config family should expose an optional validation hook through a
stable field and repo-local default path, for example:

```jsonc
"validation_script": "${env:WORKING_DIR}/.cloud-agent/validate-cloud"
```

The validation hook is not part of normal cloud startup. It exists so the
shared validation flow can run the same project-local check convention for any
repository after transfer, setup, install, and runtime startup.

And sync-down entries should map directly to predictable bundled paths such as:

```jsonc
"sync_down_profiles": {
  "working-tree-patch": {
    "cloud_export_script": "${env:CONFIG_DIR}/cloud-agent/profiles/sync_down/working-tree-patch/cloud_export_script",
    "cloud_mark_synced_script": "${env:CONFIG_DIR}/cloud-agent/profiles/sync_down/working-tree-patch/cloud_mark_synced_script",
    "local_apply_script": "${env:CONFIG_DIR}/cloud-agent/profiles/sync_down/working-tree-patch/local_apply_script"
  }
}
```

That keeps the config and filesystem structure aligned:

- `transfer_up/<profile-id>/<script-key>`
- `sync_down/<profile-id>/<script-key>`

Repo-local hooks should not need bundled wrapper scripts. The application should check whether the configured path exists before attempting to run or package it.

Projects should not need to define repo-specific transfer/setup/sync-down
profiles just to:

- stage `.env` or other explicit local-only files
- install dependencies in the cloud workspace
- run project-specific cloud validation

Those customizations should normally live in the standard repo-local hook
conventions under `.cloud-agent/`.

## Notes For Implementation

- Preserve behavior first, then simplify shape and naming.
- Keep the task boundary explicit: `0121.1` defines the hook and its config
  contract, but does not implement or test the full validation-command
  execution flow.

  - missing repo-local `local_stage_script` as a no-op
  - missing repo-local `install_script` as a no-op
  - missing repo-local `validation_script` as a no-op at the contract/resolution layer

  - shipped standard profile resolution using the simplified config shape
- `0121.1` should stop at config-contract, resolver, and runtime-shape coverage. The shared validation command and its end-to-end success/failure test matrix belong to `tasks/20260429-cloud-agent-orchestrator/0121.2-cloud-validation-command-and-bundled-runtime-assets.md`.

- The documentation update here should read like a real reference, not just release notes:
  - explain every cloud-agent config option touched by this task
  - document the standard repo-local hook conventions
  - show a complete example config
  - explain where application-level quick-start docs stop and plugin-level reference docs continue
- Each bundled script header should be short and consistent so users can scan and customize them quickly.
