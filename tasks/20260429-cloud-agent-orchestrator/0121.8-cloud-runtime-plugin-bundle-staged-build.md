# Cloud Runtime Plugin Bundle Staged Build
Build the cloud runtime image with a Linux-specific preinstalled plugin bundle
so bundled/default plugins and their dependencies are installed at Docker build
time instead of during cloud runtime startup.

## Requirements checklist

- [ ] Create or factor a reusable cloud runtime plugin bundle builder that can
  resolve selected default-config plugin names and descriptor-declared local
  workspace dependencies.
- [ ] Use a staged Docker build for the cloud runtime bundle so wheels and
  dependencies are built in a Linux runtime-compatible environment.
- [ ] Point the final cloud runtime image `BUILTIN_PLUGINS` at preinstalled
  descriptor/resource metadata, not raw plugin source trees.
- [ ] Preserve resources referenced by default config, including
  `cloud-agent-app/docs/cloud-script-authoring.md`.
- [ ] Keep non-bundled/user plugins installable through the existing
  `/cloud-agent/cache/plugin_cache/plugins` path.
- [ ] Update runtime build digest/caching so plugin source, dependency metadata,
  bundle manifests, and Dockerfile changes invalidate the runtime image.
- [ ] Update source-mode and installed-bundle cloud validation paths so they use
  the same runtime plugin-bundle mechanism or intentionally documented
  equivalents.
- [ ] Add tests proving installed-bundle `validate-cloud` does not populate the
  runtime plugin cache for bundled/default plugins.
- [ ] Update docs and smoke/build tests for the new cloud runtime layout.

## Background

The installed CLI bundle already has selected bundled plugin preinstall support.
Selected plugin descriptors are staged under `_internal/bundled_plugins` with
`"preinstalled": true`, and selected plugin packages plus their dependencies are
installed into the PyInstaller environment during bundle build.

The cloud runtime image does not currently use the same model. The runtime
Docker context copies the raw repository `plugins/` tree into
`/opt/ai-agent-platform/plugins`, and the image sets
`BUILTIN_PLUGINS=/opt/ai-agent-platform/plugins`. Because those descriptors are
not marked preinstalled, runtime startup treats them as ordinary local path
plugins and installs them into `/cloud-agent/cache/plugin_cache/plugins`.

This was observed while validating the `cloud-script-author` multi-repo
installed-bundle test. The test passed, but the validation cache still contained
26 plugin-cache install directories, including bundled/default plugins.

## Proposed Direction

Use a Docker multi-stage build to produce a Linux cloud-runtime plugin bundle:

```text
cloud-runtime-plugin-bundle/
  bundled_plugins/
    <plugin>/agent_plugin.json
    <plugin>/docs-or-resources...
  wheelhouse/
    *.whl
  manifest.json
```

The final runtime image should install wheels from the wheelhouse at build time
and set:

```dockerfile
ENV BUILTIN_PLUGINS=/opt/ai-agent-platform/cloud-runtime-plugin-bundle/bundled_plugins
```

The final image should not need to install bundled/default plugins into
`/cloud-agent/cache/plugin_cache/plugins` during runtime startup. That cache
should remain available for non-bundled or user-provided plugins.

## Open Design Decisions

- Whether to materialize the cloud runtime plugin bundle as a reusable tar/zst
  artifact in release CI, or rely first on Docker layer caching and add saved
  artifacts later.
- Whether source-mode validation should generate the plugin bundle before
  `docker build`, or let the Docker builder stage create it from copied source
  inputs.
- How strict the cache assertion should be: completely empty plugin cache, or
  no cache installs for bundled/default plugin names while allowing non-bundled
  plugin installs.
