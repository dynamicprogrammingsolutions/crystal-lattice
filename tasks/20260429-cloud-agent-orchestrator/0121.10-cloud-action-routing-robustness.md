# Cloud Action Routing Robustness
Harden connection-scoped cloud proxy routing so unscoped application actions do not keep routing to an old failed default instance when a newer running instance exists on the same connection.

## Requirements checklist

- [x] Update orchestrator connection default-instance handling so adding a new instance to an existing connection replaces the default only when the current default is missing, failed, closed, or otherwise not proxyable.
- [x] Update connection default lookup so an existing bad `default_instance_id` can fall back to a running instance in the same connection instead of returning the failed default.
- [x] Preserve the current behavior when the existing default instance is still running; do not unexpectedly move traffic between healthy instances.
- [x] Keep the frontend/session-scoped action fix in place; this task is server-side robustness for unscoped/global action routes and stale connection records.
- [x] Add orchestrator regression tests for a connection with an old failed default instance and a newer running instance, proving unscoped `/connections/:connection_id/proxy/actions` does not route to the failed instance.
- [x] Add or update tests proving session-scoped routes still resolve by session id and do not regress.
- [x] Document the routing behavior briefly in the orchestrator/cloud routing docs if there is an existing relevant section.

## Background

A live cloud session exposed a stale default-instance case:

```text
connection_id: conn_RB5u9XCepyabPApy
default_instance_id: inst_sJNBXRSOG2Iigd6_   # old failed readiness-timeout instance
instance_ids:
  - inst_sJNBXRSOG2Iigd6_
  - inst_t7dSBy8CUoiWDs6O                   # newer running instance
```

The newer instance was ready, but unscoped proxy calls went through:

```text
POST /connections/conn_RB5u9XCepyabPApy/proxy/actions
```

Those calls returned `503 runtime_not_ready` because the connection default still pointed at the old failed instance.

The frontend SDK already has a session-scoped action path from `f1e6ea61 Add session-scoped action endpoint for cloud-routed session actions`:

```text
POST /sessions/{session_id}/actions
```

When the UI element is session-scoped and the frontend supplies `context.sessionId`, the SDK should use that path. This task is about making the orchestrator robust even when an action is global/unscoped, the app build is stale, or a UI path loses session context.

## Relevant Code

Current router behavior falls back to the connection default when the proxy path has no session id:

```elixir
# cloud-orchestrator/lib/cloud_orchestrator/router.ex
defp resolve_connection_proxy_instance(conn, connection_id, path) do
  case session_id_from_proxy(conn, path) do
    nil ->
      ConnectionRegistry.default_instance(connection_id)

    session_id ->
      case ConnectionRegistry.resolve_route(connection_id, session_id) do
        {:error, :not_found} -> ConnectionRegistry.default_instance(connection_id)
        other -> other
      end
  end
end
```

Current connection default lookup uses the recorded default id:

```elixir
# cloud-orchestrator/lib/cloud_orchestrator/connection_registry.ex
def handle_call({:default_instance, connection_id}, _from, state) do
  reply =
    with {:ok, connection} <- fetch_connection(state, connection_id),
         {:ok, instance_id} <- default_instance_id(connection),
         {:ok, instance} <- InstanceRegistry.get_internal(instance_id) do
      {:ok, instance}
    end

  {:reply, reply, state}
end
```

And non-running instances produce the observed 503:

```elixir
# cloud-orchestrator/lib/cloud_orchestrator/instance_registry.ex
def handle_proxy_request(instance, conn, _path) do
  conn
  |> put_resp_content_type("application/json")
  |> send_resp(503, Jason.encode!(%{error: "runtime_not_ready", instance: public_instance(instance)}))
end
```

Connection registration currently uses a "first default wins" shape:

```elixir
Map.put("default_instance_id", connection["default_instance_id"] || instance_id)
```

The fix should avoid depending on frontend behavior alone and should make stale connection records self-healing for proxy routing.
