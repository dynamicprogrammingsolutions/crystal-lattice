## Background

The current local validation implementation can run the configured runtime
image, but the default-image build fallback still uses heuristic discovery:
`find_runtime_build_root()` walks near runtime-layout paths and checks for a
source repository shape containing `core/python`, `application/python`,
`plugins`, and `cloud-orchestrator/runtime/python/Dockerfile`.

That heuristic works in a source checkout but does not describe the installed
bundle case. The project already has a better place for this information:
`agent_terminal_app/runtime_layout.json`. The development command installed by
`nox -s install_dev_local` uses the source layout from the editable
`application/python` package, while the production bundle writes a generated
bundled layout in `scripts/build_crystal_lattice_binary.py`.

The runtime build contract should therefore be explicit in the runtime layout
and optional command overrides, not inferred by parent-directory search.

## Completion Notes

Added during completion.

- Source and bundled runtime layouts now declare explicit cloud runtime build
  context and Dockerfile paths; validation no longer searches parent directories
  for a source checkout.
- The binary build now stages `_internal/cloud_runtime` as a Docker-buildable
  context and includes it in the PyInstaller data payload.
- Runtime image validation computes a deterministic digest from declared build
  inputs, tags builds with both the configured image and an immutable digest tag,
  and labels images with `org.crystal-lattice.cloud-runtime.digest`.
- Default/local runtime images rebuild only when missing or digest-stale.
  Existing custom runtime images are trusted, while missing custom images require
  explicit runtime build overrides.
- Docker validation tests now use a test-owned runtime image tag and never remove
  `cloud-agent-runtime:latest`.
- Cloud runtime workdir coverage again exercises Codex apply-patch/workdir
  behavior inside the cloud workspace.
- Frontend profile e2e fixtures were updated to the simplified `.env` handoff
  and now use a stable validation cache directory.
- Bundle smoke coverage checks the packaged runtime build context directly and
  avoids relying on `validate-cloud --help`, which intentionally still performs
  full command/application initialization.
