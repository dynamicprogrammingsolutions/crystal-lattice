Improve the `cloud-script-author` agent so it is guided to create and run fast
local tests before final cloud validation, while keeping detailed how-to
instructions in documentation and recording authoring-process telemetry in the
real-model tests.

## Background

`0121.5` added the `cloud-script-author` agent and real-model installed-bundle
validations for both a simple project and a two-git-repository fixture. Those
tests prove that generated artifacts can eventually pass `validate-cloud`, but
they do not yet measure whether the model followed a healthy authoring process.

The default config already defines an `openai` provider using the
`openai_responses` plugin. The authoring agent should use that provider. The
installed-bundle tests should normally use that provider's normal config. The
test suite loads the repo-root `.env`, so provider API keys can come from the
usual local environment. To use a saved ChatGPT login, the person running the
test must explicitly set
`CHATGPT_CREDENTIALS=/path/to/auth/chatgpt-auth.json`; this should force
ChatGPT auth for the request rather than silently falling back.

Recent runs showed useful process signals:

- The model initially generated plausible hooks without running its own local
  test harness.
- In the multi-repo fixture, it first copied the sibling repository through
  `local-stage` instead of creating a custom transfer profile.
- After documentation was tightened, it generated a solid git-driven custom
  transfer profile, but missed sync-down compatibility until the guide called
  that out explicitly.
- The final test assertion caught these issues, but the authoring process
  itself should become more observable so documentation can be tuned based on
  what the model actually struggles with.

## Guidance Split

Keep the developer/system message short. It should describe behavior and
constraints, for example:

```text
Read the bundled cloud script authoring guide before writing hooks. Use normal
project guidance such as AGENTS.md, README files, package manifests, and tests
to infer fresh-checkout setup. Follow the guide's testing workflow: create and
run fast local tests for generated hooks/custom profiles, then run
crystal-lattice validate-cloud when Docker is available. If the guide is
insufficient, inspect the cloud-agent plugin source only as needed and report
what was unclear.
```

Put detailed recipes in `plugins/cloud-agent-app/docs/cloud-script-authoring.md`.
The docs can include step-by-step instructions, shell snippets, JSON examples,
local test harness examples, and troubleshooting notes.

## Fast Local Test Harness

The docs should explain a no-Docker inner loop for generated scripts. A typical
harness should:

- create temporary local, transfer, stage, and cloud workspace directories
- initialize any needed git repositories in temporary locations
- run `local-stage`, `local_transfer_script`, and `cloud_setup_script` directly
  with documented environment variables such as `LOCAL_WORKSPACE_DIR`,
  `TRANSFER_DIR`, `TRANSFER_STAGE_DIR`, and `CLOUD_WORKSPACE_DIR`
- assert the cloud workspace layout, copied local-only files, git state,
  sibling repository placement, and dirty working-tree preservation
- run quickly enough to be useful before the final Docker validation

The docs should point at existing standard-profile test examples:

- `plugins/cloud-agent-app/tests/test_cloud_agent_app_plugin.py` contains fast
  tests that execute bundled transfer/setup/sync scripts directly against
  temporary git repositories.
- `application/python/tests/test_cloud_validation_command_docker.py` contains
  slower Docker-backed `validate-cloud` examples and should be treated as final
  validation guidance rather than the inner loop.

## Telemetry Design

The current real-model test mostly waits for files and then validates them. To
observe authoring quality, extend the harness to read session messages/events
after completion or consume the relevant event stream while the request runs.

Collect at least:

- total tool calls
- tool calls by name
- files read
- files written/modified
- whether the bundled authoring guide was read
- whether plugin source under `cloud-agent-app/src` was read
- whether existing test examples were read
- whether a fast local harness was generated
- whether syntax checks or fast local tests were run
- whether `validate-cloud` was attempted by the model
- failures encountered before final success

Suggested initial budgets:

- Standard single-repo fixture:
  - soft limit: 20 tool calls
  - hard limit: 45 tool calls
- Multi-repo custom-transfer fixture:
  - soft limit: 40 tool calls
  - hard limit: 80 tool calls

Treat these as starting points. The completing agent should adjust them based
on actual hosted-model behavior and note the reason in completion notes.

Runtime/plugin installation issue observed:

- The installed app bundle uses `_internal/bundled_plugins` and rewrites
  selected plugin descriptors with `"preinstalled": true`, so the app-side
  local-path resolver imports those plugins directly instead of installing them
  into a cache.
- The cloud runtime Docker build context is prepared separately by
  `prepare_cloud_runtime_build_context`, which currently copies the raw
  repository `plugins/` tree into `/opt/ai-agent-platform/plugins`.
- In the runtime container, `BUILTIN_PLUGINS=/opt/ai-agent-platform/plugins`.
  Those descriptors are not marked preinstalled, and the install bypass in
  `PipTargetInstallStrategy._maybe_activate_bundled_source` only recognizes a
  root named `bundled_plugins`.
- As a result, runtime startup can run normal `pip install --target` operations
  into `/cloud-agent/cache/plugin_cache/plugins` for bundled plugins and their
  local workspace dependencies. The passing run still created 26 plugin-cache
  install directories.
- This should be addressed in the installer/runtime dependency follow-up rather
  than hidden by larger test timeouts. The soft timeout remains the guardrail:
  a pass after soft timeout should be treated as functionally successful but
  performance-suspect.
