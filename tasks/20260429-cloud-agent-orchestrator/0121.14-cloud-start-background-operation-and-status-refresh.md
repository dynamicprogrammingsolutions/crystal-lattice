# Cloud Start Background Operation And Status Refresh
Refactor cloud session startup so the user-facing action returns immediately, stores a background operation reference in session metadata, and updates metadata as the operation progresses. Replace manual status-id/token entry with status/refresh actions driven from session metadata.

## Requirements checklist

- [x] Make `cloud.start_session_agent` return immediately after scheduling startup work, before staging/uploading/creating the cloud instance completes.
- [x] Store a cloud startup operation reference in `session.metadata.cloud_agent` so later refresh/status actions can find the in-progress operation.
- [x] Run the existing local stage, transfer, upload, instance create, and readiness/status work in a background operation owned by the local application runtime.
- [x] Update session metadata from the background operation as stages progress, when the orchestrator returns instance details, and on completion/failure.
- [x] Replace the current manual "Check cloud status" dialog with status/refresh behavior that reads from session metadata and operation state.
- [x] Show instance id in the status display when available so server logs are easy to find.
- [x] Do not show or ask for the cloud token in user-facing UI.
- [x] Keep frontend UI changes generic; do not add cloud-specific refresh code to mobile or shared UI.
- [x] Add plugin/application tests for immediate return, operation ref persistence, background metadata updates, and status/refresh behavior before and after instance creation.

## Background

The current cloud start action is too synchronous for mobile use. It performs local staging, transfer creation, upload, transfer-ready signaling, instance creation, and a short readiness poll before returning. If the phone screen turns off or the request takes long enough, the message screen can miss session metadata updates and continue showing stale action state until the sessions list is refreshed.

The immediate metadata refresh issue is handled generically by `tasks/20260602-generic-session-context-refresh-for-ui-actions.md`. This cloud-specific task should focus on making cloud startup itself a proper background operation and on making cloud status/refresh read from session metadata rather than from manually entered values.

## Desired Cloud Metadata Shape

Use `session.metadata.cloud_agent` as the durable UI/status record. Suggested fields:

```json
{
  "cloud_agent": {
    "operation_ref": "cloud-start:<session_id>:<uuid>",
    "state": "starting",
    "startup_stage": "queued",
    "operation_started_at": 123.0,
    "updated_at": 123.0
  }
}
```

As the background worker progresses, merge in fields such as:

```json
{
  "instance_id": "inst_...",
  "connection_id": "conn_...",
  "session_id": "local-session-id",
  "orchestrator_url": "https://...",
  "status_url": "https://.../instances/inst_...",
  "connection_link": "crystal-lattice-cloud://...",
  "state": "running",
  "startup_stage": "ready",
  "startup_error": null,
  "startup_error_detail": null
}
```

The token may remain in metadata only if required by existing connection/action mechanics, but it must not be requested from or displayed to the user.

## Desired Operation Model

Add a small cloud operation registry stored under `app.get_runtime_store()`, for example under a plugin-owned key such as `cloud_agent_operations`.

The registry should:

- create operation refs.
- track operation state/stage/error and useful timestamps in memory.
- submit or run the background worker.
- expose a snapshot for status actions.
- tolerate missing in-memory operation state by falling back to session metadata and orchestrator status when `instance_id` is available.

`cloud.start_session_agent` should:

- validate/load session and workspace configuration.
- create and save an operation ref in session metadata immediately.
- schedule the background worker.
- return an action result with `mutations.updated_session_ids` and `ui_effects.reload_session_ids`.
- return a display saying startup has been queued/started.

The background worker should reuse the existing code path where practical:

- local stage script.
- local transfer script.
- session export.
- runtime config transfer.
- cloud runtime script packaging.
- managed SSH upload.
- transfer ready.
- instance create.
- metadata update after instance create.
- status/readiness polling if still useful, but no user-facing action should block on it.

## Desired Status/Refresh Behavior

Remove or replace the manual dialog that asks for instance id/token.

The user-facing status action should:

- take `session_id` from `$session.session_id`.
- read `session.metadata.cloud_agent`.
- if only `operation_ref` exists, show operation state/stage from the registry and metadata.
- if `instance_id` exists, fetch latest orchestrator `/instances/{instance_id}` and update metadata.
- show the instance id when available.
- show operation ref when instance id is not yet available.
- show stage/error details.
- not show token.

The existing `cloud.check_session_agent` can either be replaced by a new `cloud.refresh_session_agent` / `cloud.show_session_agent_status` pair, or kept internally for backward compatibility while the UI uses the new session-driven action. Prefer new names if that keeps old behavior from leaking into the UI.

## Testing Notes

- Background worker updates metadata to include stage progress.

- Status action before instance creation shows operation ref/stage and no token.

- Existing sync/close actions still work with metadata produced by the background worker.

Add an integration/e2e follow-up if needed:

- Starting cloud from the mobile/API action returns quickly.
- A later generic session context refresh sees updated `cloud_agent` metadata without navigating to the sessions list.
