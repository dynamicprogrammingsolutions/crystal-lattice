# Cloud Validation Command And Bundled Runtime Assets
Add a standard local-Docker cloud validation command that uses bundled runtime assets, exercises the shared cloud transfer/setup/install flow without the orchestrator, and optionally runs a repo-local validation hook. This task also makes the current repository the first real adopter of that shared validation flow.

This task is the execution half of the validation-hook work: it implements the
command that runs the hook, packages the runtime assets it needs, and owns the
end-to-end success/failure test matrix for the validation flow.

## Background

The cloud-orchestrator MVP currently owns the runtime container assets:

- `cloud-orchestrator/runtime/python/Dockerfile`
- `cloud-orchestrator/runtime/python/runtime.py`

That works for orchestrated cloud sessions, but it does not give the bundled
CLI a self-contained way to validate project cloud hooks locally because the
orchestrator service is not part of the standard CLI bundle.

The desired validation path is:

- run from the normal CLI
- use local Docker
- exercise the shared standard cloud transfer/setup/install contract
- avoid depending on the orchestrator service
- optionally run a repo-local `.cloud-agent/validate-cloud`

This task should also make the current repository the first real user of that
flow by adding repo-local hooks for:

- staging the root `.env`
- installing the project according to the repository README
- validating the prepared cloud workspace through the shared command

This task should therefore create a shared validation workflow that is useful
for every project adopting the cloud hook conventions, while also preparing for
the future plugin-driven runtime ownership model.

The preceding task defines the validation hook contract. This task is where
that contract becomes executable:

- implement the command
- execute the hook in the real flow
- add the Docker/runtime packaging needed for that flow
- prove with tests that each stage is actually exercised

## Proposed Direction

The command shape can be refined during implementation, but it should be a real
CLI entry such as:

```bash
crystal-lattice validate-cloud
```

or an equivalent subcommand/flag exposed through a generic command contribution
surface owned by the CLI or application layer.

The command should:

1. Resolve the standard cloud profile configuration for the current workspace.
2. Run the same local staging and transfer script contract used for cloud
   startup.
3. Materialize the runtime transfer bundle.
4. Build or run the bundled validation runtime container locally with Docker.
5. Wait for runtime readiness.
6. Run a built-in generic smoke check inside the prepared cloud workspace or
   runtime.
7. Run the optional repo-local validation hook if present.
8. Return success only when every step exits cleanly.

The built-in generic smoke should stay deterministic and provider-free. For
example, it may verify that:

- the runtime became ready
- the cloud workspace exists
- the transfer/setup/install steps completed

Exact smoke assertions can be refined during implementation, but they should
not require hosted providers or the orchestrator service.

After the generic smoke passes, the optional repo-local validation hook should
run in the prepared cloud environment. For this repository, that hook should be
the first real end-to-end use of the shared flow, rather than a test-only
surrogate.

Unlike `0121.1`, this task should not stop at config or documentation shape.
It should implement and exercise the full validation flow.

## Command Contribution Surface

The current terminal slash command registry in
`application/python/agent_terminal_app/terminal.py` is static. This task should
introduce a reusable extension surface so plugins can contribute CLI commands
without hardcoding each new command in the terminal or top-level CLI parser.

The final abstraction can be refined, but it should be closer to the
application/plugin layer than to core `FeaturePlugin` request hooks, because
this command is about local tooling, Docker, and workspace/runtime lifecycle
rather than prompt/request behavior.

## Bundled Runtime Assets

Because the standard CLI bundle already packages application default-config
assets but not the orchestrator runtime directory, this task should duplicate
the runtime assets into a packaged location owned by the CLI/application/plugin
side.

The duplication is intentional for now. The immediate goal is:

- the standard CLI bundle can run cloud validation locally
- the runtime asset path is stable and packaged
- the future plugin-driven runtime transition is unblocked

The duplicated Dockerfile should switch to a more capable Ubuntu-class base and
install the standard Python toolchain plus common utilities needed by the
standard and repo-local scripts.

Even while the files are duplicated, the two runtime Dockerfiles should remain
intentionally the same in behavior and package set:

- the orchestrator-owned Dockerfile under `cloud-orchestrator/runtime/python/`
- the bundled CLI/plugin-owned duplicate used by the validation flow

This task should treat divergence between those two Dockerfiles as a bug unless
and until runtime ownership is fully moved away from the orchestrator package.

## Project Hooks For This Repository

This repository should adopt the standard hook conventions as part of this
task, without creating a project-specific cloud profile. The initial hooks
should cover:

- `.cloud-agent/local-stage` to stage the root `.env`
- `.cloud-agent/install-cloud` to set up the venv and install the project per
  the repository README
- `.cloud-agent/validate-cloud` to validate the prepared environment through a
  deterministic project-level check

The goal is for this repository to prove that the shared validation mechanism
works for a real project, not just for synthetic fixtures.

## Testing Notes

Testing for this task should be explicit and layered:

- unit tests for command discovery, config resolution, hook selection, error
  mapping, and command contribution wiring
- Docker-backed integration tests for the validation command without the
  orchestrator, covering:
  - successful validation of a fixture workspace
  - failure from an invalid local-stage hook
  - failure from an invalid transfer/setup/install/validate hook
  - failure reporting when runtime startup or validation exits non-zero
- Docker-backed e2e coverage in the cloud orchestrator fixture flow, covering:
  - fixture projects that include a validation hook
  - invoking the validation command in the fixture workspace
  - success fixtures and failure fixtures
  - assertions that failures are actually caught, so the e2e flow proves the
    validation command is checking each script rather than only exercising a
    happy path

Failure coverage should be designed to prove that each script stage actually
participates in the validation flow. At minimum, include fixtures where:

- the local-stage or transfer behavior is wrong in a way that prevents a file
  such as `.env` from reaching the cloud workspace, and the validation hook
  fails because that file is missing
- the cloud setup step is wrong and validation fails because the workspace was
  not materialized correctly
- the install step is wrong and validation fails because the expected
  environment or dependency state was not created
- the validation hook itself fails and the command surfaces that failure

These fixtures should guard against false-positive implementations where the
validation command accidentally bypasses one script stage, hardcodes file
placement, or otherwise succeeds without exercising the real shared contract.

There is intentionally no constraint limiting this to a single Docker-backed
test. Multiple Docker integration and e2e tests are appropriate when they
cover distinct success and failure behavior.

## Execution plan

Added during task completion after plan approval.

1. Extend the application-plugin surface so actions remain the executable
   contract and commands become frontend bindings to those actions:
   `get_actions()` / `execute_action()` define the real operation and inputs,
   while a new command-contribution method defines CLI and later slash-command
   metadata that maps parsed arguments onto an existing action id.
2. Update the main `crystal-lattice` CLI to discover plugin-contributed
   commands after config/plugin loading, register them as real top-level
   subcommands, and dispatch them through the existing application action
   execution path rather than through a second command-specific execution API.
3. Add a `cloud.validate_cloud` application action in `cloud-agent-app`, and
   have the plugin contribute a `validate-cloud` command descriptor that binds
   the CLI surface to that action with command-specific help and argument
   parsing.
4. Implement the local-Docker validation flow behind that action so it reuses
   the shared transfer/setup/install/runtime packaging path, starts the bundled
   runtime container without the orchestrator, waits for readiness, runs a
   built-in deterministic smoke check, then runs the optional packaged
   validation hook.
5. Duplicate the runtime Dockerfile and Python runtime entrypoint into a
   packaged plugin-owned asset location included in the standard CLI bundle,
   while keeping the orchestrator-owned copies working and intentionally in
   sync.
6. Update both runtime Dockerfiles together to use the same Ubuntu-class base
   image and installed toolchain, and add runtime-side validation endpoints and
   structured stage/failure reporting so setup/install/validate failures are
   surfaced clearly.
7. Add this repository's own `.cloud-agent/local-stage`,
   `.cloud-agent/install-cloud`, and `.cloud-agent/validate-cloud` hooks as the
   first real adopter of the shared validation flow, using the standard
   profiles instead of repo-specific cloud profile definitions.
8. Add layered coverage:
   unit tests for command contribution/discovery and validation action logic;
   Docker-backed integration tests for the local validation command success and
   failure matrix; bundle tests proving the packaged runtime assets and command
   ship in the standard distribution; and cloud orchestrator fixture e2e
   updates that place validation hooks in fixture workspaces and invoke the
   validation command there to prove each script stage is actually exercised.
