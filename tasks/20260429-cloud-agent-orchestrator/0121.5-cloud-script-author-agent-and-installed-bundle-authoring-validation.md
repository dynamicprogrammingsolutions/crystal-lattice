# Cloud Script Author Agent And Installed Bundle Authoring Validation
Add a default specialized agent that helps projects create standard
`.cloud-agent` hooks from ordinary project guidance, bundled cloud-agent
documentation, and filesystem inspection. Prove the flow from an installed
bundle using the bundled default config, including the runtime-image build path
from packaged `_internal/cloud_runtime` assets.

## Background

The cloud validation command and bundled runtime assets now exist, and
`tasks/20260429-cloud-agent-orchestrator/0121.4-cloud-validation-runtime-image-build-cleanup.md`
changed the runtime-image build path so source and bundled layouts expose
explicit runtime build metadata. The binary build now stages a Docker-buildable
`_internal/cloud_runtime` context and the bundled runtime layout points at that
context.

That resolves the design issue where `validate-cloud` could only auto-build the
default runtime image by searching for a source checkout containing
`core/python`, `application/python`, `plugins`, and
`cloud-orchestrator/runtime/python/Dockerfile`.

However, there is still a missing acceptance test: the bundle smoke test checks
that `_internal/cloud_runtime` exists and appears in `--runtime-layout-json`, but
it does not run bundled `validate-cloud` in a way that proves Docker can build
the runtime image from those packaged assets.

This task should add that missing installed-bundle runtime-build test and then
build on it with a real-world authoring validation. The final validation should
prove that a user with only the installed package and default config can ask a
specialized agent to create project cloud hooks, and then use the bundled
validation command to confirm those hooks work.

## Desired Authoring Model

The fixture project's `AGENTS.md` should not be a cloud requirements document.
It should look like ordinary project guidance that a coding agent would already
consume:

- what the project does
- how to set up dependencies after a fresh checkout
- whether a local `.env` is expected for integration-style checks
- how to run basic tests or validation
- any relevant repo layout notes

The cloud-specific knowledge should come from the specialized agent's
system/developer message and the bundled cloud-agent authoring docs. The agent
should combine:

- project facts from `AGENTS.md`, README, and filesystem inspection
- the cloud hook contract from bundled docs
- the user's generic request

The expected generated standard hooks for a simple fixture are:

- `.cloud-agent/local-stage`: stage required local-only files such as `.env`
- `.cloud-agent/install-cloud`: install dependencies in the cloud workspace, for
  example `npm install` or `python -m venv .venv` plus `pip install`
- `.cloud-agent/validate-cloud`: run deterministic project validation in the
  prepared cloud workspace

For more complicated projects, the docs should also explain when a project may
need `.cloud-agent/cloud-agent.json` and custom transfer profiles, such as a
multi-repository workspace that needs specialized transfer behavior. That
advanced case can be documented in this task without needing to be the first
real-model acceptance scenario.

## Installed-Bundle Runtime-Build Acceptance Details

Add a Docker-backed installed-bundle acceptance test before the real-model
authoring test. The test should:

1. Build or use the Linux binary bundle through the existing binary
   distribution test path.
2. Extract or install the bundle in a clean test location.
3. Create a small fixture workspace with already-written minimal `.cloud-agent`
   hooks.
4. Use the bundled default config path created by the installed command or a
   copied bundled default config, preserving the bundled runtime layout.
5. Select a test-owned runtime image tag through project
   `.cloud-agent/cloud-agent.json` or an equivalent safe override.
6. Run bundled `crystal-lattice --runtime-layout-json` and assert it reports a
   bundled layout with `_internal/bundled_plugins` and `_internal/cloud_runtime`.
7. Run bundled `crystal-lattice validate-cloud --workspace-dir <fixture>
   --cache-dir <tmp-cache>`.
8. Assert output includes `Cloud Validation Passed`.
9. Inspect the test-owned Docker image and assert it has the
   `org.crystal-lattice.cloud-runtime.digest` label.
10. If practical and stable, run validation a second time and assert the
    digest-matching image is reused rather than rebuilt.

The critical guardrail is that this test must not pass
`--runtime-build-context <repo-root>` or `--runtime-dockerfile
<repo-root>/cloud-orchestrator/...`. It should exercise the installed bundle's
runtime layout.

## Real-Model Authoring Validation Details

The real-model validation should be gated by explicit environment/marker flags
because it requires Docker, a built bundle, and provider credentials. It should
prefer a cheap hosted model and low-cost settings. The validation should:

1. Start from an installed or extracted binary bundle.
2. Create a fresh fixture workspace with no `.cloud-agent/local-stage`,
   `.cloud-agent/install-cloud`, or `.cloud-agent/validate-cloud` scripts.
3. Include normal project guidance in `AGENTS.md`; do not place cloud-hook
   instructions there.
4. Start the bundled app/server or use its HTTP/session APIs in a way that uses
   the bundled default config.
5. Create a session with the specialized cloud-script author agent.
6. Send a generic prompt such as "Create cloud installation scripts for this
   project."
7. Override the model/reasoning settings for cost control.
8. Wait for the generated scripts to appear.
9. Assert the scripts are executable and contain plausible project-specific
   behavior.
10. Run bundled `validate-cloud` against the fixture.
11. Assert validation passed and that the stage/install/validate paths were
    actually exercised, for example by checking files or markers produced by
    each script.

## Suspension Notes

Added during task completion after integration-test pushback.

Implementation was previously suspended while running the installed-bundle
integration tests. The first bundle validation attempt exposed a real bundled
plugin dependency issue: default config loads `openai_responses`, but bundled
plugin paths activated source trees directly instead of installing plugin
project dependencies, so the installed bundle failed with `No module named
'openai'`.

Adding `openai` to `crystal-lattice-cli` dependencies was rejected and reverted
because it breaks plugin package boundaries and hides the generic bundle
dependency problem. Dependency task
`tasks/20260429-cloud-agent-orchestrator/0121.6-selected-bundled-plugin-preinstall-and-bundle-e2e.md`
resolved this by preinstalling selected bundled plugin packages and their
descriptor-declared local workspace dependencies.

The installed-bundle cloud validation test was also changed away from the
nested-Docker approach. It now runs the installed bundle directly on the host
and lets `validate-cloud` use host Docker normally.
