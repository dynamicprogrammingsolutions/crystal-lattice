# Prepare A Publishable Homepage With A Clear Product Overview

Replace the unfinished homepage prototype and overlong UI walkthrough with a
concise, screenshot-led explanation of the application. Every retained visual
slot must use reviewed real-product proof, each image must teach one clear
relationship, and the visitor must understand the product before reaching the
six-step Getting Started path.

## Requirements checklist

- [ ] The hero and opening copy let an unfamiliar visitor identify Crystal
      Lattice as an application for running and organizing persistent AI-agent
      sessions on the visitor's computer. Primary language explains the
      product and benefit before introducing model-native, provider, plugin,
      harness, runtime, or configuration terminology.
- [ ] Before Getting Started, a concise application overview explains four
      relationships in this order:
      1. work in an agent session through a familiar conversation and composer;
      2. organize persistent sessions as recognizable work;
      3. configure how an agent behaves through profiles, provider-specific
         settings, plugins, and tools; and
      4. continue the same runtime session from Desktop and mobile clients.
- [ ] The overview is a product explanation rather than an exhaustive control
      tour. Composer actions, Message actions, Session actions, detailed
      connection methods, and other power-user controls appear only when they
      strengthen a distinct overview claim; otherwise they move to a later
      deep dive, documentation, or the rejected set.
- [ ] The session visual is one continuous, unsliced product screen with a
      short visible conversation, the composer naturally at the bottom, and
      readable model, reasoning-effort, and web-search controls. Copy may
      explain that the selected profile and enabled extensions/features can
      contribute controls and that stars select frequently used controls.
- [ ] The workspace visual uses one coherent real Desktop state to show
      descriptive session titles/subtitles, pinning, durable task status, and
      current request state without requiring a second status-only image.
- [ ] The configuration story uses the smallest number of images that remain
      legible at actual page size. It distinguishes the agent profile,
      provider-specific settings, enabled plugins, and tools without shrinking
      several complete windows into one unreadable collage.
- [ ] The cross-device visual shows one truthful session in Desktop and mobile
      with matching session identity, agent/profile, task status, prompt, and
      response. It contains no raw UUIDs or unrelated technical metadata, and
      mobile availability is described according to maintained release state.
- [ ] Every retained image has one declared visitor-facing purpose, a direct
      interface-oriented title, useful alt text, and a concise caption that
      tells the visitor what relationship to notice. Captions contain no task,
      fixture, crop, provenance, checkpoint, or review language.
- [ ] Homepage screenshots follow one maintained visual system modeled on the
      existing **Provider-specific behavior can become real UI.** proof:
      recognizable source context, readable proof-bearing UI, consistent
      canvas/background/border treatment, and at most one genuine focus
      callout when magnification is necessary.
- [ ] Screenshots use one sanitized fixture and consistent product identity,
      theme, and standard blue accent where the product surface permits it.
      Light/dark variants remain truthful real UI; processing may crop, dim,
      frame, arrange, or magnify genuine pixels but may not repaint controls or
      values.
- [ ] Every retained public visual slot has a reviewed image. The normal
      homepage renders no **Planned visual** panel, missing-proof placeholder,
      review-status label, disabled fake form, or intentionally blank
      screenshot canvas. Redundant placeholder-bearing sections may be removed
      instead of receiving unnecessary images.
- [ ] The approved product values remain represented without requiring six
      equal feature cards: model-family-oriented profiles, replaceable plugin
      surfaces, transparent operation, cross-device continuity, adaptability
      beyond development, and durable session workspaces.
- [ ] **Provider-specific behavior can become real UI.** remains the quality
      benchmark. Its provider settings and usage/cost proof may be reused,
      moved, or incorporated into the configuration/transparency story when
      doing so avoids duplicate claims.
- [ ] Getting Started retains exactly six ordered steps: install CLI, start a
      workspace, download Desktop, connect Desktop, get the mobile app, and
      connect from mobile.
- [ ] The default Desktop startup path binds locally. Same-network discovery
      and LAN exposure are introduced separately, state that another device
      can reach the runtime, and include a trusted-network qualification.
- [ ] The Desktop connection step includes a compact real connection-editor
      and recognizable connected outcome using port `9000`.
- [ ] Steps 5–6 form a visibly related **Mobile access** group. The connection
      explanation presents automatic local discovery first, address and port
      as the fallback, and bridge access away from the local network third,
      using genuine connection UI rather than three equally prominent command
      fragments.
- [ ] Current downloads, public/tester/invite availability, compatibility
      limitations, bridge state, security implications, and open-source claims
      derive from maintained product or release evidence.
- [ ] Material after Getting Started has a distinct visitor and purpose.
      Detailed bridge deployment, compatibility reference material,
      plugin-authoring instructions, SDK examples, or repeated feature proof
      moves to documentation or a focused route when it interrupts the first
      user path. Knowingly unverified examples are not published.
- [ ] The complete candidate is responsive, keyboard accessible, semantically
      ordered, reduced-motion aware, and understandable without hidden primary
      content, autoplay, unlabeled dots, or required swipe interaction.
- [ ] The complete page is visually reviewed in light and dark themes at
      desktop, tablet, and phone widths. Important UI and callouts remain
      readable at rendered page size, and Getting Started is reachable without
      traversing an excessive product-reference tour.
- [ ] Maintained landing-package documentation records the selected page
      sequence, visual-purpose map, asset ownership, responsive behavior,
      release cuts, and reasons for the final choices.
- [ ] No source push, waitlist deployment, AWS mutation, production website
      publication, or visual-source promotion occurs before its explicit human
      checkpoint. Subtask `020` continues to own the real waitlist and final
      integrated publication.

requires a user-visible Desktop, mobile, backend, or plugin behavior change,
stop and obtain approval for that product change rather than fabricating the
state in image processing.

## Execution plan

Status: Approved

Restructure the homepage around one short first-user narrative rather than a
control-by-control tour:

1. A plain-language hero establishes the product category, primary benefit,
   local ownership, and immediate next action.
2. A static screenshot-led overview explains session work, persistent
   workspace organization, agent configuration, and cross-device continuity.
3. Getting Started provides the first-success path.
4. Only distinct, verified secondary material remains after setup.

The overview should use ordinary document flow at every width. A small image
gallery is allowed only when a single story genuinely needs two complementary
views and both remain discoverable without interaction. Primary product
understanding must not depend on a carousel, tab state, autoplay, or swipe.

Start by writing a visual-purpose map before changing assets. For every current
placeholder and candidate, record the user question, one claim, selected real
source, required processing, final destination, and disposition. Remove slots
whose only purpose duplicates another story.

Use the existing provider proof as the visual grammar:

- recognizable context;
- one obvious focal relationship;
- readable genuine labels at page size;
- consistent outer presentation;
- focus callout only when the source context would otherwise make the target
  unreadable.

Produce the first contextual candidate without promoting sources:

- revise the hero and overview content model;
- build the continuous Composer/session proof;
- select and refine the single Workspace proof;
- compare one-image and two-image configuration treatments;
- recompose the Desktop/mobile continuity proof;
- temporarily bind all four stories to the actual homepage;
- show the proposed destination or removal of each former placeholder.

Stop for the Overview Storyboard checkpoint. After approval, move accepted
sources into the captured-image lifecycle, add or update catalog definitions,
generate light/dark responsive derivatives, and replace all retained normal
homepage placeholders.

Then revise Getting Started. Keep the ordinary Desktop command local, add the
real Desktop connection proof, group Mobile access, reorder the mobile
explanation, and process the genuine mobile connection source. The future
waitlist position must communicate availability without rendering a fake form
or internal implementation status.

After the First-user Flow checkpoint, audit everything below Getting Started.
Retain only material with a verified claim, a distinct audience, and a clear
next route. Move detailed operations/reference content to maintained
documentation rather than duplicating it on the homepage.

Finish with production-build content scans, catalog and freshness checks,
responsive browser tests, direct image inspection, accessibility checks,
release/download verification, and privacy/sanitization review. Promote only
the final human-approved sources, then hand the local site to subtask `020`
without pushing or publishing.
