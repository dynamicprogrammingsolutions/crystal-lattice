## Review checklist

- [ ] The repository changes are limited to the requested task-file work.
- [ ] The task starts with a title, short description, and requirements checklist.
- [ ] Requirements describe verifiable outcomes rather than execution steps.
- [ ] Existing requirements were preserved unless the user approved a change.
- [ ] Factual research and supporting details needed to interpret the requirements were retained.
- [ ] Open questions are classified as requirement questions or design decisions.
- [ ] Requirement questions were not silently answered or used to change the requirements.
- [ ] The stored execution plan, when expected, preserves important decisions and rationale without redundant detail.
- [ ] The plan satisfies each requirement without broadening, narrowing, or reinterpreting it.
- [ ] Requirement verification maps important requirements to evidence and identifies test type and boundary.
- [ ] Internal implementation tests do not overwhelm the user-facing summary.
- [ ] Documentation is addressed separately with audience, scope, and rationale.
- [ ] User-visible behavior, interfaces, ownership, extraction boundaries, scope, tests, and documentation decisions are exposed for review.
- [ ] The user-facing response is self-contained and easier to review than the full stored plan.
- [ ] Execution did not begin without authorization.
